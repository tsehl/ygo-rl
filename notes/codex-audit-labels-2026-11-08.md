# Audit de huit scripts utilisant les labels

Échantillon reproductible : huit scripts tirés avec la graine 20261108 parmi les 161 dont le premier refus du traducteur combiné était `méthode :SetLabel sur Eff`. Ce nombre décrit uniquement le premier refus, pas le gain qu'apporterait une nouvelle représentation.

Les usages observés dépassent le label booléen temporaire actuellement porté par le maillon : valeur 100 puis remise à zéro dans une condition (50619462), valeur d'ATK d'une carte sélectionnée (74711057), choix 0/1 réutilisé plus tard (35011819), nombre de cartes et label multiple contenant un code (59131526), joueur responsable (87340664), et indicateurs remis à zéro à des moments différents (2295440, 87210505). Le script 43711255 utilise aussi un objet associé à un label.

La représentation doit distinguer la durée de vie propre à l'effet, les valeurs associées à un maillon et, lorsque nécessaire, les valeurs multiples ou objets référencés. Un seul booléen de chaîne ne suffit pas. Les effets de bord dans une condition doivent être comparés à l'oracle ; les variantes non représentées doivent continuer à être refusées. Cet audit ne prétend pas que ces huit cartes deviendront traduisibles avec le seul label.

Cas précis supplémentaire pour Cattle Call : `spcost` écrit 100 y compris lors de la vérification de coût, puis `sptg` lit et remet ce label à zéro dans `chk == 0`. Les vérifications coût puis cible doivent donc partager une valeur pendant leur évaluation ; simplement enregistrer un label au moment de la résolution ne suffit pas. Il faut établir par des sondes natives quelles écritures de ces vérifications persistent au-delà de la génération des actions, avant de choisir la représentation.

Une sonde native reproductible (`tests/label_check_oracle_reference.py`) vérifie deux parties : la vérification de coût écrit 100, la vérification de cible le lit puis écrit 0, le paiement lit 0 et écrit 200, le ciblage réel lit 200 et écrit 300, puis la résolution lit 300. Les deux activations résolvent effectivement l'effet attendu. Cette sonde établit le comportement du noyau natif, pas encore une implémentation JAX.

La sonde native `tests/label_menu_persistence_oracle_reference.py` établit aussi que les écritures du contrôle de coût survivent à la génération du menu : pour une même graine, une magie incrémente son label à chaque contrôle `chk == 0`. Son activation immédiate lit 1 ; si le joueur invoque d'abord un monstre puis active cette même magie, elle lit 2. Le contrôle lors du premier menu a donc modifié durablement l'effet, même si cette action n'a pas été choisie. La sonde vérifie les résolutions et l'absence d'erreurs Lua. Cette observation impose de traiter explicitement ces effets de bord dans la génération des actions ; elle ne suffit pas à décrire tous les moments où l'oracle effectue ces contrôles.

La sonde `tests/label_rejected_cost_oracle_reference.py` vérifie un cas supplémentaire : même lorsqu'un coût écrit un label puis retourne `false`, l'écriture reste visible pour un autre effet qui conserve une référence au premier. Il ne suffit donc pas de sauvegarder les mutations des seuls candidats déclarés légaux. Le code natif `effect::clone` copie le vecteur de labels par valeur ; `GetLabel` renvoie 0 pour un vecteur vide et toutes les valeurs sinon, tandis que `SetLabelObject` accepte une carte, un effet, un groupe ou une table. Ces observations contraignent la représentation mais ne couvrent pas encore les durées de vie des objets référencés.
